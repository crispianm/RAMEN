## Result first

**No check was found that is VACUOUS in the strict sense of the two earlier cases (wrong class / same value on both branches).** The data-level checks (Downtown TS2, VK655, SiLog sentinel, hinge) all FAIL when the feature is broken. But five checks are **WEAK**, i.e. they cannot fail for a plausible defect, and one of them (first-run item 1, the cosine-decay point) cannot detect the very error it exists to detect:

1. **WEAK/near-VACUOUS: `check_first_run.sh` item 1 cannot tell S3 (cosine to 0 at 14000) from a constant 1e-4 LR.** The only decay probe is step 12200 (expected 9.93e-05) with a 1.5 % tolerance (`check_first_run.sh:38-39`, `abs(got/ref-1) <= 0.015`). 1.00e-04 is only 0.70 % away. Forced fail 1b (log edited to `lr=1.00e-04` at 12200, i.e. a no-decay/S2 schedule): **checker reports ok, exit 0**. Steps after 12200 are not probed at all (1e: lr 9.32e-05 -> 5.00e-05 at step 12420: no FAIL). What it would have hidden: a run that trained at a flat 1e-4 for 2000 steps, or that decayed wrongly after 12200, passing the stop check. Fix idea: add table points late in the cosine (e.g. steps 13000 and 13900, values computed from `make_lr_scale`) and/or tighten tolerance to 0.3 %.
2. **WEAK: nothing asserts the hinge FLOOR value (80 vs 300) or any declared VALUE.** `arms.py` EXPECT is a *set of differing keys*, not values (`arms.py:~82-90`); `smoke.py` c5 computes `expected_pred10` from `cfg["loss"]["sky_hinge_min_depth"]` of the same yaml it feeds the loss (`smoke.py` c5 loop), so it is self-referential for the floor; `check_first_run.sh` item 3 checks key presence and finiteness only. Forced fails (a1): H300 floor 300 -> 30, VK655 bound 656 -> 700, TS2 `ts2_sky` True -> False, A0b seed 49 -> 50 all give `ALL EXPECTED DIFFS EXACT: True`; and item 3 given H300's metrics under the H80 arm (3f) or the reverse (3g) says ok. The values are correct today (grep of the yamls: H80 80.0, H300 300.0, VK655 656 + flag true, A0b seed 49, TS2 ts2_sky true; real-run hinge values H300 ~3x H80 are consistent), but only because someone read them; the config sha pin in `train_template.sbatch:63-65` pins whatever yaml is committed. What it would have hidden: a mis-typed floor in the yaml shipped as the "H300" arm.
3. **WEAK: `smoke.py` has no assertions (except `ca[1:] == ct[1:]` crop equality).** Every claim (masks differ, equals `ts_v2_guarded` to 0.0, VK655 mask 100 %, sentinel in SiLog mask, hinge expected value) is a number written to `smoke_results.json` and read by a human. I wrote verdict functions (`verdict.py`, `verdict45.py`) and they do detect every injected break (below), so the numbers are meaningful, but the script itself can never "fail". Same for `classes.py`: it records class names and exits 0.
4. **WEAK: `classes.py` (check 1b).** Docstring promises "per-source fallback" (`classes.py:3-4`); not implemented: the build aborts at the first source that raises, and ScanNet++ (last source) raises on this machine in every arm (`FileNotFoundError ... sem_test.txt`, `classes.json` `build_error`), so its class and flags are never verified and a genuine new error is indistinguishable from this standing error. Forced fail (`classes_ff.py`: recipe VKITTI class swapped to base `VKITTIDataset`): train.py's own guard raises (`metric_supervision needs resize_mode: vda with degrade on`), recorded as an `error` record, `classes.py` still exits 0. The guard in train.py, not classes.py, is what protects.
5. **WEAK (stale citations): README section 4 file:line claims.** Spot check of 8 `train.py` citations: at the commit that wrote them (f235107) 477-480 and 1219-1223 are right; 395, 436/576, 1073, 1225, 1541 are off by +2 (line shift after the table-sha log lines were added in the same commit); 1236 and 1529 are +2 from the real clamp use sites (1238, 1531), but the "metric_depth_clamp" definition is at 1165, not what the row cites. At HEAD (after 56644ca, `make_lr_scale`) the SiLog/clamp/scale-anchor/METRIC_EPS rows are off by 30-40 lines (e.g. `silog_ceil` is now train.py:1251-1254; `METRIC_EPS_MAX_DEPTH` 1574; `scale_anchor` td<=80 at 1106; `effective_depth_bound` 397). The claims themselves are TRUE at every line I resolved (silog_ceil per source, no clamp upper bound, 80 m constants inactive in C3).

**Additional finding, not a vacuous check but a mislabeled number (scorer regression):** `scorer/regression_c3_n46_step12000_*/compare.txt` shows `DIFF VKITTI far 80-655 pred:gt EXACT pooled median: new 0.863392 earlier 0.841730 rel 2.57e-02 tol 3e-03`. README (scorer, line 23) says the exact value differs from the 100k-subsample one "by sampling error only (expected < 0.003)". A 2.6 % gap is 8x that bound, and with ~10^6 pooled samples the median's sampling error is far below 1e-3, so the cause is almost certainly weighting (the legacy statistic caps each clip at 100k px, the exact one is pixel-weighted), not sampling. The success-rule quantity `abs_dev = |1-median|` is built from the EXACT value (0.1366 vs 0.1583 legacy, 14 % apart). I did not re-derive per-clip contributions (needs the GPU run); flag it so the success threshold is stated against the exact statistic, and the "sampling error" wording is not used to dismiss the DIFF row.
